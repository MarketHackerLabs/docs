# Design: добавление товаров в контроле остатков + пункт меню в Admin

Дата: 2026-08-26  
Статус: approved for planning  
Модули: `product_matching`, `stock_control` (manager-portal); `admin-panel` (навигация / параметры)

## Проблема

1. **Manager Portal.** Соответствия артикулов сейчас можно завести только загрузкой CSV/XLSX: файл сразу пишется в БД через `POST …/product-matching/import`. Нет способа набрать или поправить строки в интерфейсе перед сохранением; физический остаток задаётся отдельно на доске.
2. **Admin.** Параметры контроля остатков (сейчас TTL каталога WB Content) лежат карточкой на общей странице `/settings`, а не отдельным пунктом в зоне «Продукт», как «Анализ отзывов» или «ИИ-аудит карточки».

## Цель

1. Объединить ручное добавление и импорт из файла в одном модальном черновике-таблице с проверкой и явным «Подтвердить».
2. При подтверждении сохранять соответствия и, при указании, физический остаток на складе.
3. Вынести настройки контроля остатков в отдельный пункт меню Admin.

## Вне scope

- Редактирование уже сохранённых строк matching вне этого потока (отдельный CRUD UI)
- Массовое удаление SKU / listings
- Синхронизация остатков на витрины маркетплейсов (только физический склад)
- Отдельная админская витрина «список организаций / джобов» для stock control
- Изменение семантики advice/alerts и cadence sync
- Seller TTL UI (остаётся только Admin)

## Решение

### A. Manager Portal — модалка «Добавить товары»

**Вход:** кнопка «Добавить товары» на `/stock-control` (только owner). Карточка «Соответствие артикулов» с кнопками «Шаблон» / «Загрузить» **заменяется** этим потоком.

**Модалка — редактируемая таблица:**

| Колонка | Обязательность | Смысл |
|---------|----------------|--------|
| SKU | да | внутренний артикул |
| WB | хотя бы одно из WB/Ozon | артикул Wildberries |
| Ozon | хотя бы одно из WB/Ozon | артикул Ozon |
| На складе | нет | физический остаток; целое ≥ 0 или пусто |

**Действия в модалке:**

- добавить / удалить строку;
- «Из файла» — CSV/XLSX; парсинг **без записи в БД**; строки **append** к черновику;
- «Шаблон» — скачать шаблон с четырьмя колонками (`SKU,артикул WB,артикул Ozon,На складе`); колонка остатка в файле необязательна;
- «К ошибке» — циклический переход к следующей проблемной строке;
- «Подтвердить» — доступна только при **нуле** ошибок валидации и непустом наборе валидных строк;
- отмена — закрыть без записи.

**Валидация черновика (клиент + повтор на сервере):**

- правила matching как в `matching_import` (SKU обязателен; ≥1 marketplace; дубликаты WB/Ozon внутри пакета; комментарии `#` в SKU);
- «На складе»: пусто **или** целое ≥ 0;
- проблемные строки **остаются** в таблице с подсветкой; Confirm заблокирован, пока есть ошибки;
- быстрый переход к проблемным строкам.

**Лимит черновика: 2000 строк** (ручные + из файлов). При превышении — понятное сообщение; лишние строки не добавляются. Лимит согласован на клиенте и сервере.

**Поведение «На складе» при Confirm:**

- заполнено → после upsert matching: `ensure_sku` + установка физического остатка (`ledger/set`);
- пусто → только matching; существующий `physical_qty` **не** меняем (новый SKU без явного остатка остаётся с дефолтом склада, как после текущего import + первого открытия доски).

### B. Backend — commit вместо «файл сразу в БД»

**Новый endpoint (owner):**  
`POST /organizations/{org_id}/product-matching/commit`

Тело: массив строк `{ internalSku, wbSku?, ozonSku?, warehouseQty? }` (имена в стиле существующих API).

Поведение:

1. Если строк 0 или > 2000 → ошибка валидации.
2. Серверная валидация всего пакета; при любой ошибке — **ничего не пишем** (all-or-nothing), ответ с `issues[]` (row, field, message).
3. При успехе в одной транзакции (или эквивалентной атомарности модуля): upsert product + listings; для строк с `warehouseQty` — ensure stock SKU + set qty.
4. Ответ успеха: `{ committed: N }` (и при необходимости краткая сводка).

**Парсинг файла на клиенте** предпочтителен для UX черновика. Допустимо опционально добавить `POST …/product-matching/parse` (без записи) для единого парсера xlsx/csv на бэкенде — решение в плане реализации; семантика та же: только разбор → строки черновика.

**Текущий `POST …/import`:** убрать из UI. В плане: либо удалить endpoint, либо оставить внутренним/deprecated без вызова из portal. Цель — один пользовательский путь записи: commit.

**Шаблон:** обновить `GET …/template` под четыре колонки (`SKU`, WB, Ozon, «На складе»); заголовки согласованы с парсером (остаток в файле опционален).

### C. Admin — пункт меню «Контроль остатков»

По образцу «Анализ отзывов» / «ИИ-аудит»:

1. В `sidebar.tsx` зона «Продукт»: пункт **«Контроль остатков»**, `match: ["/stock-control"]`.
2. Дочерний пункт **«Параметры»** → `/stock-control/settings`.
3. Страница настроек: текущее поле «TTL каталога WB Content (часы)» (и будущие platform-параметры модуля).
4. Карточку «Контроль остатков» **убрать** с общей `/settings`.
5. Данные: без дублирования ключей platform settings — UI читает/пишет существующий `stockControl` / `stock_control_wb_content_catalog_ttl_hours` (через текущий `GET|PATCH /admin/settings` или тонкий `/admin/stock-control/settings`, который делегирует в platform settings). Предпочтение плану: минимальный diff — отдельная страница UI на том же API, без нового backend-модуля, пока нет иных admin-сущностей.

Org override TTL на странице организации **не** переносится в этот пункт (уже на org detail).

## Затрагиваемые области

| Репозиторий | Области |
|-------------|---------|
| `manager-portal` | `/stock-control` page, modal component, `api.ts` |
| `backend` | `product_matching` (commit, template, parser qty column); возможно deprecate import; `stock_control` ledger set из commit |
| `admin-panel` | `sidebar.tsx`, `stock-control/settings` page, убрать карточку с `/settings` |
| `docs` | `architecture/stock-control.md` / product-matching при необходимости |

## Критерии приёмки

1. Owner открывает «Добавить товары», вручную добавляет строки, подтверждает — на доске появляются SKU; при указанном остатке он отображается на складе.
2. Файл с валидными и невалидными строками попадает в таблицу целиком; Confirm недоступен; «К ошибке» ведёт к проблемным; после правок Confirm сохраняет пакет.
3. Файл с >2000 строк (или черновик сверх лимита) отклоняет превышение с понятным текстом.
4. Пустой «На складе» не затирает уже заданный остаток существующего SKU.
5. Confirm с ошибками валидации на сервере не частично пишет matching.
6. В Admin есть пункт «Контроль остатков» → «Параметры» с TTL; на общей `/settings` карточки модуля нет.
7. Тексты для продавца без жаргона API/внутренних имён.

## Риски

| Риск | Митигация |
|------|-----------|
| Большой JSON commit (до 2000 строк) | Лимит 2000; таймаут/батч в плане при необходимости |
| Расхождение клиентской и серверной валидации | Общие правила; сервер — источник истины, all-or-nothing |
| Парсинг xlsx только на клиенте | Опциональный parse endpoint; иначе проверенная библиотека / перенос логики |
| Пользователи привыкли к мгновенному import | UX: явный Confirm; подсказка в модалке |

## Открытые решения для плана (не блокируют design)

- Клиентский парсер vs `POST …/parse`
- Точное имя полей JSON commit
- Удалить `POST …/import` сразу или оставить deprecated один релиз
- Нужен ли отдельный `/admin/stock-control/settings` или только новая страница на `/admin/settings`
