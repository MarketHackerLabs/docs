# Design: размеры WB (nm → sizes) на доске контроля остатков

Дата: 2026-08-26  
Статус: approved for planning  
Модули: `product_matching`, `stock_control`, Manager Portal

## Проблема

На Wildberries одна карточка (`nmID`) содержит несколько размеров (`chrtID`), у каждого свои баркоды и выставленные остатки. Сейчас продавец в matching указывает один идентификатор на строку; часто путают nm и chrt. На доске размеры одной карточки не сгруппированы; нет сценария «ввёл nm — получил все размеры».

Ozon: каждый размер — отдельный SKU площадки; авто-связка размеров WB↔Ozon в v1 не делается.

## Цель

1. При добавлении товаров колонка WB принимает **nmID**; система разворачивает все размеры карточки в отдельные строки схемы **SKU | WB | Ozon**.
2. На доске размеры одной nm видны **группой** (шапка + вложенные размеры).
3. Физический остаток и алерты — **на каждый размер** (отдельный внутренний SKU). Уведомления — по каждому size-SKU, как сейчас.
4. Matching с Ozon остаётся ручным: колонка Ozon на строке размера; после expand она пустая, пока продавец не заполнит.

## Вне scope

- Авто-матч размеров Ozon ↔ WB
- Баркоды в UI / matching
- Выбор WB-кабинета в модалке при нескольких токенах (см. правила резолва ниже)
- Смена cadence sync, advice-формул, FBO
- Guided Connect

## Решение

**Expand nm при parse/commit + группировка доски по `catalog_id` (nm).** Схема данных matching не меняет смысл колонок: одна строка = один внутренний SKU + опционально WB listing (`mp_sku = chrt`) + опционально Ozon listing.

### Каталог Content

Расширить персист кэша кабинета (сейчас только `chrt_id → nm_id`):

| Поле | Смысл |
|------|--------|
| `marketplace_account_id` | Кабинет |
| `nm_id` | nmID карточки |
| `chrt_id` | chrtID размера |
| `tech_size` | techSize из Content (nullable/пустая строка) |
| `wb_size` | wbSize при наличии (nullable, опционально в v1) |

Уникальность: `(marketplace_account_id, chrt_id)`. Индекс по `(marketplace_account_id, nm_id)` для expand.

Источник: `POST /content/v2/get/cards/list` — из `sizes[]` читать `chrtID`/`chrtId`, `techSize`, при наличии `wbSize`. Баркоды (`skus`) в v1 не обязательны к сохранению.

Правила refresh TTL — как у текущего Content-каталога. Перед expand, если nm нет в кэше: принудительный refresh кабинета (или ошибка строки, если после refresh nm всё ещё нет).

### Добавление товаров (модалка / parse / commit)

**Ввод WB:** числовой **nmID**. UI-подсказка: артикул карточки WB (nm), не chrt и не баркод.

**Развёртка одной входной строки** `{baseSku, wbNm, ozonSku?, qty?}`:

1. Резолв кабинета: среди WB-кабинетов org с **active** API-токеном найти те, в чьём каталоге есть `nm`.  
   - 0 → ошибка строки «карточка не найдена в кабинете».  
   - 1 → использовать его.  
   - >1 → ошибка строки «карточка в нескольких кабинетах» (v1 без выбора кабинета).
2. Для каждого размера `(chrt, tech_size)` из каталога построить строку matching:
   - `internal_sku = {baseSku}/{tech_size}` если tech_size непустой, иначе `{baseSku}/{chrt}`;
   - `wb_sku` / listing `mp_sku = chrt` (строка), `catalog_id = nm`;
   - `ozon_sku` = значение из входной строки **только если у nm ровно один размер**; если размеров >1 — Ozon на всех развёрнутых строках **пустой** (входной ozon игнорируется или даёт предупреждение — предпочтительно: ошибка/предупреждение «Ozon укажите после развёртки по размерам», либо молча очистить; **решение: молча не копировать Ozon при N>1**, при N=1 — копировать);
   - physical qty из колонки — **одинаково на каждый** размер; пусто = не трогать.
3. Лимит 2000 применяется к **числу строк после развёртки**.
4. Дубликаты internal_sku / mp_sku — по существующим правилам validate.

**Файл / ручной ввод:** та же семантика колонки WB = nm.

**Обратная совместимость данных:** уже сохранённые listing с `mp_sku = chrt` остаются валидны. Старый смысл «в колонку ввели chrt» в новом UI **не поддерживается** — только nm.

### Доска

- API board: либо группы на бэке (`BoardGroup` по nm + `sizes[]`), либо плоский список size-SKU с полями `wbNmId`, `techSize` для группировки на клиенте. Предпочтение: **поля на size-SKU + группировка в Portal** (меньше ломки пагинации); пагинация v1 — по size-SKU как сейчас, группы могут рваться между страницами (приемлемо) **или** пагинация по nm-группам (лучше UX, больше работы).  
  **Решение v1:** пагинация и поиск как сейчас по size-SKU (`internal_sku`); Portal группирует **видимую страницу** по `catalog_id`/`wbNmId`. Поиск по nm — если `q` совпадает с nm, показывать size-SKU этой карточки (расширить поиск board).
- Шапка группы: фото (nm), nmID, кол-во размеров, индикатор attention если любой ребёнок в attention.
- Строка размера: internal_sku, techSize, physical/available, склады, advice.
- Без WB `catalog_id`: одиночные строки (Ozon-only / необогащённые).

### Алерты и Telegram

Без смены fingerprint/зернистости: low_stock / oversell / rebalance на `stock_control_skus` размера. Отдельное «сводное на nm» не делаем.

### Sync

Без смены hot path: matched chrt из listing; stocks по chrt; catalog refresh пишет расширенные поля sizes.

## Данные / миграции

- Расширить `stock_control_wb_catalog_entries` (или заменить набор колонок): добавить `tech_size` (и опционально `wb_size`); `nm_id` уже есть.
- Alembic: nullable `tech_size` default `''`; backfill пустым; полный refresh перезапишет.
- `product_matching` / `stock_control_skus` схема без ломки уникальности.

## Ошибки (продавцу)

| Случай | Поведение |
|--------|-----------|
| WB не число / пусто при наличии SKU | как сейчас / «укажите nm карточки» |
| nm нет в каталоге | строка с ошибкой, commit blocked |
| nm в >1 кабинете с токеном | ошибка строки |
| нет активного WB-токена при WB-колонке | ошибка «сначала сохраните ключ кабинета» |
| после expand >2000 строк | ошибка лимита |

## Тесты

- Expand: nm с 3 sizes → 3 products/listings; tech_size в internal_sku; Ozon не копируется при N>1; копируется при N=1.
- Каталог парсер: sizes → chrt, nm, techSize.
- Board: size-SKU отдают nm + techSize; Portal группирует.
- Sync: stocks по развёрнутым chrt (регрессия matched-only).
- Алерты: low/oversell на одном размере не требуют других размеров той же nm.

## Документация

Обновить `docs/architecture/stock-control.md` и `product-matching.md`: WB ввод = nm; listing `mp_sku` = chrt; доска группами.

## Критерии готовности

1. Добавление nm создаёт по одному size-SKU на каждый chrt карточки.
2. Matching остаётся SKU | WB(chrt в БД) | Ozon; Ozon вручную на размер.
3. Доска показывает группу nm → размеры.
4. Алерт/Telegram на размер у порога уходит отдельно.
5. Старые chrt-listing продолжают sync.
