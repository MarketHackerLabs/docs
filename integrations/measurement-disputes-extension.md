# Клиент: оспаривание обмеров WB (extension)

Базовый URL: `{API}/api/v1/measurement-disputes`  
OpenAPI: `{API}/docs` (tag `measurement-dispute`)  
Архитектура бэкенда: [measurement-disputes.md](../architecture/measurement-disputes.md)  
Требования: [tz_osparivanie.md](../../tz_osparivanie.md) · Дизайн: [2026-11-26-measurement-disputes-design.md](../superpowers/specs/2026-11-26-measurement-disputes-design.md) · Кейсы: [2026-11-27-measurement-dispute-cases-design.md](../superpowers/specs/2026-11-27-measurement-dispute-cases-design.md)

**Код расширения в этой поставке не меняется.** Backend, Manager Portal и admin-panel готовы. Модалку в расширении делает другой разработчик, по этому документу. Общего UI-пакета с Manager Portal нет: расширение реализует интерфейс само.

**Breaking change (2026-11-27).** Модель «задача = элемент списка» заменена на родительский кейс и дочерние задачи. Старые эндпоинты `POST /`, `GET /`, `GET /active`, `GET /{id}`, `GET /{id}/result`, `POST /{id}/cancel` удалены. При выкладке все прежние задачи удалены без переноса (Мурлики по зарезервированным возвращены). Клиент, написанный под старый контракт, перестанет работать.

Эталонная реализация логики (парсер, группировка, срок, первое обращение, сборка запросов): `manager-portal/src/lib/measurement-dispute/`. Её можно портировать или переиспользовать как спецификацию.

## 1. Границы

| Делает расширение | Делает backend |
|-------------------|----------------|
| Читает XLSX локально, считает итоги, срок, собирает первое обращение | Чистит текст от персональных данных |
| Собирает JSON выбранного обмера или пачки обмеров | Считает и резервирует Мурлики |
| Показывает стоимость, состояния и ошибки | Вызывает модель, проверяет JSON по схеме |
| Опрашивает статус, показывает результат, копирует тексты | Возвращает результат или безопасное сообщение об ошибке |

MarketHacker ничего не отправляет в кабинет WB. Кнопки «Отправить в WB» нет, есть только копирование.

## 2. Авторизация

```http
Authorization: Bearer <accessToken>
X-MarketHacker-Client: browser_extension
Content-Type: application/json
```

- JWT access + refresh — как в остальном API расширения, см. [authentication.md](../architecture/authentication.md) и [auth-mfa-client.md](./auth-mfa-client.md).
- Доступ: активный пользователь + фича тарифа `measurement_dispute`. Фича `browser_extension` для этих эндпоинтов **не требуется**.
- `X-MarketHacker-Client` в эндпоинтах `measurement-disputes` не проверяется. Заголовок нужен для единообразия с другими запросами расширения и для каталога тарифов (`GET /billing/plans`).
- Тела и ответы — **camelCase**. Успех: `{ "data": …, "meta": {} }`. Список: `{ "data": […], "meta": { "total", "page", "pageSize", "hasNext", "requestId" } }`.
- Ошибка: `{ "error": { "code", "message", "details?" } }`.
- Даты в запросах — `YYYY-MM-DD`. Время в ответах — ISO 8601.

## 3. Контракт API

**Кейс** — одно оспаривание по загруженному отчёту. **Задача (job)** — один ИИ-запуск внутри кейса (`analyze_response` или `photo_analysis`). Повторный анализ в том же отчёте — новая задача в том же кейсе. Новый файл или «Начать заново» — новый кейс. Мурлики списываются за задачу, не за кейс.

| Метод | Путь | Назначение | Успех |
|-------|------|------------|:-----:|
| `POST` | `/cases` | Создать кейс при загрузке отчёта | 201 |
| `GET` | `/cases` | Список кейсов (`page` ≥ 1, `pageSize` 1…100, default 20) | 200 |
| `GET` | `/cases/active` | Кейсы с задачей `queued` / `running` | 200 |
| `GET` | `/cases/{caseId}` | Кейс и его задачи | 200 |
| `POST` | `/estimate-cost` | Стоимость в Мурликах | 200 |
| `POST` | `/cases/{caseId}/jobs` | Создать задачу в кейсе | 202 |
| `GET` | `/jobs/{jobId}` | Статус задачи | 200 |
| `GET` | `/jobs/{jobId}/result` | Результат (только `succeeded`) | 200 |
| `POST` | `/jobs/{jobId}/cancel` | Отмена | 200 |

Чужой кейс или чужая задача отдаются как `404`. Удаления кейса в API нет.

Порядок для расширения: загрузили XLSX → `POST /cases` → сохранили `caseId` → `POST /estimate-cost` → `POST /cases/{caseId}/jobs` → опрос `GET /jobs/{jobId}` → `GET /jobs/{jobId}/result`.

### 3.0. Кейс

#### `POST /cases` → `201`

Создаёт кейс. Нужна фича `measurement_dispute` (иначе `403`). В теле только шапка и итоги листа; строки XLSX на сервер не уходят.

| Поле | Тип | Обязательный | Описание | Пример |
|------|-----|:------------:|----------|--------|
| `title` | string, 1…256 | да | Подпись в списке: имя файла или «Демо-отчёт» | `"Отчёт по удержаниям.xlsx"` |
| `fileLabel` | string, 1…512 | да | Имя файла или демо, как в интерфейсе | `"Отчёт по удержаниям.xlsx"` |
| `sheetName` | string, 1…128 | да | Имя листа | `"Лист1"` |
| `isDemo` | boolean | нет (default `false`) | Демо-отчёт | `false` |
| `reportSummary` | ReportSummary | да | Итоги листа («Итого по файлу») | |
| `organizationId` | UUID \| null | нет | Организация. Пользователь должен в ней состоять. Квоту резервирует задача, а не кейс | |

`ReportSummary`: `operations` (int ≥ 0), `uniqueMeasurements` (int ≥ 0), `articles` (int ≥ 0), `accrued` (number), `storno` (number), `net` (number), `moneyWarnings` (int ≥ 0). Это те же поля, что в итогах файла на клиенте (раздел 6).

Ответ `data` — `CaseSummary` (у нового кейса `status = "draft"`, `jobs = []`).

#### `GET /cases`, `GET /cases/active`, `GET /cases/{caseId}`

- `GET /cases` — `data` массив `CaseSummary`, новые сверху; `meta`: `total`, `page`, `pageSize`, `hasNext`, `requestId`. Фильтра по статусу нет.
- `GET /cases/active` — `data` массив `CaseSummary` только тех кейсов, где есть задача `queued` или `running`. Для виджета «Задачи в работе»: один пункт на кейс.
- `GET /cases/{caseId}` — `data` один `CaseSummary`.

`CaseSummary`:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | Идентификатор кейса (`caseId`) |
| `title` | string | Подпись в списке |
| `fileLabel` | string | Имя файла / демо |
| `sheetName` | string | Лист |
| `isDemo` | boolean | Демо-отчёт |
| `reportSummary` | ReportSummary | Итоги листа |
| `status` | `"draft"` \| `"active"` \| `"succeeded"` \| `"failed"` \| `"cancelled"` | Вычисляется на сервере по задачам |
| `jobs` | `Summary[]` | Задачи кейса, от старых к новым. Без результатов: результат — `GET /jobs/{jobId}/result` |
| `createdAt` | datetime | Создан |
| `updatedAt` | datetime | Обновлён |

Правила `status`: задач нет → `draft`; есть `queued` / `running` → `active`; иначе при любой `failed` → `failed`, при любой `succeeded` → `succeeded`, иначе → `cancelled`. Детали по запускам — в `jobs[]`.

### 3.1. `POST /estimate-cost`

Стоимость без создания задачи и без резерва.

| Поле | Тип | Обязательный | Описание | Пример |
|------|-----|:------------:|----------|--------|
| `kind` | `"analyze_response"` \| `"photo_analysis"` | да | Вид задачи | `"photo_analysis"` |
| `measurementCount` | int, 1…500 | нет (default `1`) | Число обмеров с фото. Для `analyze_response` игнорируется | `10` |

Ответ `data`: `{ "units": 30 }` — стоимость в Мурликах.

Проверяет те же правила, что и создание: вид задачи включён (иначе `400`), для фото число обмеров не больше лимита пачки (иначе `400`).

### 3.2. `POST /cases/{caseId}/jobs` → `202`

`caseId` — в пути, в тело не дублируется. Кейс должен принадлежать пользователю, иначе `404`. Тело — объединение по полю `kind`. Организация: `organizationId` (UUID, необязательно). Если у пользователя несколько организаций с квотой Мурликов и `organizationId` не передан, придёт `409` с `error.details.code = "quota_org_required"` и списком `details.organizations[].id`. Предложите выбрать организацию и повторите запрос.

#### `kind = "analyze_response"` — разбор ответа WB

| Поле | Тип | Обязательный | Описание | Пример |
|------|-----|:------------:|----------|--------|
| `kind` | `"analyze_response"` | да | Дискриминатор | |
| `organizationId` | UUID \| null | нет | Организация, с квоты которой списать Мурлики | |
| `wbResponseText` | string, ≤ 50 000 | да | Полный ответ WB. Пустой после `trim` → `400`. Сервер обрезает до лимита из настроек (по умолчанию 8 000 символов) | `"Переобмер невозможен: товар отсутствует на складе…"` |
| `previousAppealNumber` | string ≤ 64 \| null | нет | Номер первого обращения | `"12345678"` |
| `article` | string ≤ 64 \| null | нет | Артикул | |
| `sourceSheet` | string ≤ 128 \| null | нет | Лист XLSX | `"Лист1"` |
| `sourceRow` | int ≥ 1 \| null | нет | Строка XLSX | `14` |
| `measurementDate` | date \| null | нет | Дата обмера | `"2026-11-02"` |
| `measuredDimensions` | Dimensions \| null | нет | Габариты по обмеру WB | |
| `declaredDimensions` | Dimensions \| null | нет | Габариты в карточке | |
| `sellerDimensions` | Dimensions \| null | нет | Контрольный обмер продавца | |
| `discrepancyReason` | string ≤ 1000 \| null | нет | Причина спора, подтверждённая пользователем | |
| `reportPublicationDate` | date \| null | нет | Дата размещения отчёта, подтверждённая пользователем | `"2026-11-10"` |
| `calculatedDeadline` | date \| null | нет | Дата размещения + 7 календарных дней | `"2026-11-17"` |
| `stockStatus` | `"in_stock"` \| `"out_of_stock"` \| `"unknown"` | нет (default `"unknown"`) | Остаток товара | |
| `newSupplyDate` | date \| null | нет | Дата новой поставки | |
| `penaltyAmount` | number ≥ 0 \| null | нет | Сумма удержания | `1250.5` |
| `currency` | string ≤ 8 | нет (default `"RUB"`) | Валюта | |
| `attachments` | Attachments | нет | Какие подтверждения есть у продавца | |
| `ruleContext` | string ≤ 8 000 \| null | нет | Выдержка правил. **Не передавайте**: тогда сервер подставит проверенный текст из настроек | |

`Dimensions` (все поля необязательные, ≥ 0): `widthCm`, `lengthCm`, `heightCm` — сантиметры; `volumeLiters` — литры.

`Attachments` (boolean, default `false`): `xlsx`, `wbPhoto`, `sellerPhotos`, `reportDateProof`.

Не передавайте XLSX, значения других строк и персональные данные покупателей.

#### `kind = "photo_analysis"` — анализ фото

| Поле | Тип | Обязательный | Описание |
|------|-----|:------------:|----------|
| `kind` | `"photo_analysis"` | да | Дискриминатор |
| `organizationId` | UUID \| null | нет | См. выше |
| `items` | PhotoMeasurementItem[], 1…500 | да | Обмеры. Для одного фото — массив из одного элемента |

`PhotoMeasurementItem`:

| Поле | Тип | Обязательный | Описание |
|------|-----|:------------:|----------|
| `measurementNumber` | string, 1…64 | да | Номер замера |
| `article` | string ≤ 64 | нет (default `""`) | Артикул / номенклатура |
| `photoUrl` | string ≤ 2048 | да по смыслу | Ссылка на фото. Только `https://`, иначе `400` |
| `netAmountRub` | number | да | Итог по обмеру: начисления + сторно. Должен быть > 0 |
| `hasDiscrepancy` | boolean | да | Должен быть `true` |
| `measuredDimensions` | Dimensions \| null | нет | Габариты по обмеру WB |
| `declaredDimensions` | Dimensions \| null | нет | Габариты в карточке |
| `discrepancyPercent` | number ≥ 0 \| null | нет | Процент расхождения |

Серверные ограничения (возвращают `400` с готовым текстом в `error.message`):

- пустой `items`;
- обмеров больше `maxBulkPhotos` из настроек (по умолчанию 50): предложите запускать анализ по одному обмеру;
- у обмера нет `https`-ссылки на фото, итог ≤ 0 или нет расхождения. В сообщении указан порядковый номер обмера.

Отправляйте только активные обмеры: расхождение есть, итог положительный, фото есть. Сторнированные и нулевые не отправляйте.

`Summary`:

| Поле | Тип | Описание |

| `kind` | `"analyze_response"` \| `"photo_analysis"` | Вид |

### 3.3. Активные кейсы

Список для виджета «Задачи в работе» — `GET /cases/active` (см. выше). Отдельного списка задач нет.

### 3.4. `GET /jobs/{jobId}` — статус

`data` — `Summary`. Полл: старт через 2–3 с, интервал 3 с, остановка на `succeeded` / `failed` / `cancelled`. Задача выполняется асинхронно: разбор ответа — секунды, фото — зависит от числа обмеров. Серверный предел выполнения — 25 минут, дальше задача станет `failed`, Мурлики вернутся.

### 3.5. `GET /jobs/{jobId}/result` — результат

Пока статус не `succeeded` — `409` («Результат ещё не готов»). `data`:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | |
| `kind` | string | Вид |
| `status` | `"succeeded"` | Всегда |
| `result` | AnalyzeResponseResult \| PhotoAnalysisResult | Зависит от `kind` |
| `createdAt` | datetime | |
| `finishedAt` | datetime \| null | |

#### `AnalyzeResponseResult`

| Поле | Тип | Описание |
|------|-----|----------|
| `category` | `NO_STOCK` \| `DEADLINE` \| `PHOTO_EVIDENCE` \| `MISSING_DATA` \| `ACCEPTED` \| `TEMPLATE_REPLY` \| `OTHER` | Категория ответа WB |
| `categoryLabel` | string | Подпись категории |
| `summary` | string | Краткое объяснение ответа WB |
| `wbArgument` | string | На что ссылается поддержка |
| `weakPoints` | string[] | Что не рассмотрено по существу |
| `missingEvidence` | string[] | Каких материалов не хватает |
| `nextStep` | string | Следующий шаг |
| `shortReply` | string ≤ 900 | Короткий ответ для чата поддержки |
| `detailedClaim` | string ≤ 4000 | Подробная повторная претензия |
| `needsHumanReview` | boolean | Нужна ручная проверка (всегда `true` для `OTHER`) |
| `warnings` | string[] | Риски и недостающие данные; незаполненные поля — плейсхолдеры `[УКАЖИТЕ …]` |

#### `PhotoAnalysisResult`

| Поле | Тип | Описание |
|------|-----|----------|
| `items[]` | PhotoAnalysisItemResult[] | Вердикт по каждому обмеру |
| `aggregates` | PhotoAnalysisVerdictAggregates | Счётчики и суммы по вердиктам |

`PhotoAnalysisItemResult`: `measurementNumber`, `article`, `verdict` (`appeal` — есть основания, `borderline` — пограничный случай, `no_reason` — оснований не видно, `insufficient` — по фото вывод сделать нельзя), `summary`, `observableFacts` (string[]), `warnings` (string[]), `netAmountRub` (number \| null).

`PhotoAnalysisVerdictAggregates`: `appealCount`, `borderlineCount`, `noReasonCount`, `insufficientCount` (int ≥ 0); `appealAmountRub`, `borderlineAmountRub`, `noReasonAmountRub`, `insufficientAmountRub` (number ≥ 0).

Аргументы из `observableFacts` можно добавлять в черновик претензии только после `succeeded`, как проверяемые наблюдения. Не обещайте отмену штрафа.

### 3.6. `POST /jobs/{jobId}/cancel`

Тела нет. `data` — `Summary`. Задача `queued` → `cancelled`, резерв Мурликов возвращается; статус кейса пересчитывается (если других активных задач нет, кейс перестаёт быть `active`). Завершённая или уже отменённая — вернётся без изменений. `running` → `409` («Анализ уже выполняется, отменить его нельзя»).

### 3.7. Ошибки

| HTTP | Код | Когда | Что показать |
|------|-----|-------|--------------|
| 400 | `VALIDATION_ERROR` | Вид задачи выключен, пустой ответ WB, лимит пачки, нет ссылки на фото, очередь недоступна | `error.message` как есть |
| 401 | `UNAUTHORIZED` / `TOKEN_EXPIRED` | Нет токена, сессия истекла | Предложить войти снова |
| 402 | `PLAN_LIMIT_EXCEEDED` | Не хватает Мурликов | Сообщение + ссылка на смену тарифа / докупку |
| 403 | `PERMISSION_DENIED` | Нет фичи (в том числе при создании кейса) `measurement_dispute` в тарифе | «Оспаривание обмеров недоступно на текущем тарифе» + ссылка на тарифы |
| 404 | `NOT_FOUND` | Чужой или неизвестный кейс или задача | «Оспаривание не найдено» / «Задача не найдена» |
| 409 | `CONFLICT` | Результат не готов; отмена выполняемой задачи; `quota_org_required` | Сообщение из `error.message`; для организации — выбор |
| 422 | — | Тело не прошло проверку формата | Общее «Проверьте данные и повторите» без имён полей |
| 5xx | — | Сбой сервера | «Не удалось выполнить запрос. Попробуйте ещё раз» |

Клиент **не** показывает stack, имена полей схемы, статусы очереди, названия моделей и провайдера.

| Файл не выбран | «Загрузите отчёт по удержаниям или откройте демо» | Кнопки «Загрузить», «Демо» |
| Файл читается | Индикатор | Блокировка повторной загрузки |
| Файл разобран | Создаётся кейс (`POST /cases`), дальше все задачи идут в этот `caseId` | Повторная загрузка нового файла / «Начать заново» → новый кейс |
| Не найден заголовок или артикул | «Не нашли колонку артикула» | Ручной выбор колонки |
| Не найдена сумма | «Колонка суммы не найдена». **Не показывать 0 ₽** | Ручной выбор колонки |
| Нет строк по артикулу | «По этому артикулу строк нет» | Выбрать другой артикул |
| Дата размещения отчёта не подтверждена | Поле пустое, срок не показывается | Пользователь вводит дату |
| Срок истёк | Нейтральное предупреждение: «Срок мог истечь. Проверьте дату размещения отчёта и актуальные правила» | Можно продолжать |
| Нет остатка и нет даты новой поставки | В тексте остаётся `[УКАЖИТЕ дату новой поставки]` | Пользователь заполняет |
| Ответ WB пустой | Кнопка «Разобрать ответ» недоступна | Вставить ответ |
| Перед запуском | Какие данные уйдут и стоимость в Мурликах («Спишется N Мурликов») | Подтверждение |
| Задача `queued` / `running` | Индикатор, повторный клик заблокирован | «Отменить» только для `queued` |
| `succeeded` | Результат, две отдельные кнопки копирования | |
| `failed` | `errorMessage` + «Данные сохранены, можно повторить» + ручной шаблон ответа | «Повторить» создаёт **новую** задачу |
| `cancelled` | «Задача отменена, Мурлики возвращены» | |
| Нет фичи / не хватает Мурликов | Сообщение из ответа и ссылка на тарифы | |
| Копирование успешно | Локальное подтверждение, текст не исчезает | |

Подпись под результатом: «Черновик MarketHacker. Проверьте факты и актуальные правила перед отправкой».

Введённые данные должны сохраняться при ошибке и при временном закрытии модалки в пределах сессии. Выбор обмеров и черновик первого обращения хранятся на клиенте под ключом `caseId` (в Manager Portal — `mh_measurement_dispute_workspace:{caseId}`); сервер их не хранит. Если локального черновика для кейса нет, показывайте шапку и задачи с результатами из API, а выбор обмеров — после повторной загрузки XLSX в тот же кейс (без нового `POST /cases`).

## 6. Локальный XLSX (ТЗ §4–§6, §22)

Файл читается **только в браузере**. XLSX не отправляется на сервер и в модель. В запрос идут только выбранные поля.

### Разбор

- Список листов; по умолчанию первый непустой.
- Строка заголовков: просканировать первые 40 строк, взять строку с наибольшим числом совпадений с алиасами.
- Колонка артикула не найдена → ручной выбор.
- Пустые строки после заголовка игнорировать. Номер исходной строки XLSX сохранять для ссылки в обращении. Значения источника не менять.

### Колонки

| Поле | Алиасы |
|------|--------|
| Артикул | «артикул», «артикул продавца», «nmId», «номенклатура» |
| Дата обмера | «дата обмера», «дата замера», «дата измерения», «дата удержания» |
| Фактические габариты | единая колонка или длина/ширина/высота; «фактические габариты», «габариты по обмеру», «результат обмера», «действительные габариты» |
| Заявленные габариты | «габариты в карточке», «заявленные габариты», «габариты продавца» |
| Сумма | «сумма», «штраф», «удержание», «сумма удержания», «начислено» |
| Причина | «причина», «тип удержания», «основание» |
| Фото | «фото обмера», «фотография обмера», «ссылка на фото», «фото» |

Реальный отчёт WB дополнительно содержит колонки: Номенклатура, Номер замера, Предмет, Разница в габаритах, заявленные и фактические Ш/Д/В/объём, Фото замеров, Статус обмера, Дата штрафа, Сумма штрафа, Сумма сторно.

### Деньги

- Убрать пробелы, неразрывные пробелы, `₽`, `руб.`; знак сохранить.
- Запятая — десятичный разделитель, если нет иной явной структуры.
- Нечисловое значение не учитывать в сумме, но считать в предупреждениях.
- Нет денежной колонки → «Колонка не найдена», не `0 ₽`.
- Вывод: `ru-RU`, без копеек при целой сумме.

### Группировка и итоги

- Группировать по «номенклатура + номер замера». Один обмер может занимать несколько строк.
- Сумма обмера = все начисления + все сторно. Обмер с нулевым итогом после сторно в оспаривание не включать.
- «Итого по файлу»: операции, уникальные обмеры, артикулы, начислено, сторно, чистый итог.
- Артикулы считать уникальными после нормализации пробелов и регистра.
- Если по артикулу несколько обмеров, показать все строки и отметить строку с наибольшим рассчитанным объёмом. Решение остаётся за пользователем.

Контрольные фикстуры:

| Файл | Расхождений / обмеров | Артикулов | Сумма |
|------|----------------------:|----------:|-------|
| Демо | 3 | 2 | 3 400 ₽ |
| Реальный отчёт | 153 операции / 12 обмеров | 10 | начислено 165 804,50 ₽, сторно −40 401,20 ₽, итог 125 403,30 ₽ |

### Срок и первое обращение

- Срок = **подтверждённая пользователем** дата размещения отчёта + 7 календарных дней. Нельзя подменять датой обмера.
- Первое обращение собирается шаблоном, без ИИ. Блоки: просьба проверить контрольный обмер и провести дополнительный; артикул, строка XLSX, дата обмера, значения отчёта и карточки; контрольный обмер продавца в той же индивидуальной упаковке; дата размещения отчёта и срок; наличие остатка или дата новой поставки; список приложений (XLSX, фото WB, контрольные фото, подтверждение даты размещения отчёта).
- Нет даты, номера обращения, размеров или суммы → плейсхолдер `[УКАЖИТЕ …]`, значение не угадывать.
- Режимы: одно обращение по одному обмеру или общая претензия по нескольким обмерам. В общей претензии по умолчанию выбраны активные обмеры с положительным итогом; по каждому выводятся артикул, номер замера, строки XLSX, габариты WB и карточки, процент расхождения, начислено, сторно, итог, ссылка на фото; в конце — суммарная сумма.

## 7. Биллинг

1. Перед запуском вызовите `POST /estimate-cost` и покажите «Спишется N Мурликов».
   - `analyze_response`: фиксированная стоимость.
   - `photo_analysis`: `measurementCount × тариф за обмер`; `measurementCount` — число обмеров, которые уходят в `items`.
2. Создайте задачу `POST /cases/{caseId}/jobs`. Мурлики резервируются сразу.
3. Создание кейса Мурлики не резервирует. `succeeded` → списание. `failed` и `cancelled` → резерв возвращается.

Веса по умолчанию (меняются в админке, поэтому не хардкодьте, берите из `estimate-cost`):

| `action_key` | `param_key` | Default |
|--------------|-------------|--------:|
| `measurement_dispute_analyze_response` | `base` | 5 |
| `measurement_dispute_photo_analysis` | `per_measurement` | 3 |

Обработка отказов:

- `403` — нет фичи `measurement_dispute`: показать, что инструмент недоступен на текущем тарифе, дать ссылку на тарифы.
- `402` — не хватает Мурликов: показать сообщение и путь к докупке / смене тарифа.
- `409` с `quota_org_required` — показать выбор организации и повторить с `organizationId`.

## 9. Чеклист приёмки E2E (для разработчика расширения)

API и авторизация:

- [ ] Запрос без токена → `401`, UI предлагает войти.
- [ ] Тариф без `measurement_dispute` → `403`, понятное сообщение и ссылка на тарифы.
- [ ] `estimate-cost` показывает «Спишется N Мурликов» до запуска.
- [ ] Не хватает Мурликов → `402`, задача не создаётся, введённые данные сохранены.
- [ ] Загрузка файла → `POST /cases` → `201`, `caseId` сохранён.
- [ ] Чужой или несуществующий `caseId` → `404`.
- [ ] Повторный анализ в том же отчёте → новая задача в том же кейсе; в `GET /cases` одна строка, в `GET /cases/{caseId}` обе задачи.
- [ ] `GET /cases/active` возвращает кейс при `queued` / `running` и не возвращает после завершения.
- [ ] Валидный `analyze_response` → `202`, статус опрашивается до `succeeded` / `failed` / `cancelled`.
- [ ] Валидный `photo_analysis` из одного обмера → `202`.
- [ ] Пачка больше лимита → понятная ошибка, предложение запускать по одному.
- [ ] `queued` отменяется, `running` не отменяется (`409` обработан без технического текста); после отмены кейс перестаёт быть `active`.
- [ ] `failed` показывает `errorMessage`, ручной шаблон и «Повторить».

Модалка:

- [ ] Все пункты чеклиста из раздела 5.
- [ ] Закрытие по кнопке, `Escape`, подложке; при несохранённом вводе — подтверждение.
- [ ] Страница WB под модалкой не сдвигается и не теряет скролл после закрытия.

XLSX и расчёты:

- [ ] Демо → 3 расхождения, 2 артикула, 3 400 ₽.
- [ ] Реальный отчёт → 153 операции, 12 обмеров, 10 артикулов, начислено 165 804,50 ₽, сторно −40 401,20 ₽, итог 125 403,30 ₽.
- [ ] Нет денежной колонки → «Колонка не найдена», не `0 ₽`.
- [ ] Нет колонки артикула → ручной выбор.
- [ ] Срок = дата размещения отчёта + 7 дней, включая конец месяца.
- [ ] Нет даты поставки / номера обращения / размеров → в тексте `[УКАЖИТЕ …]`.
- [ ] Исходный XLSX не уходит с устройства (проверить во вкладке Network).

Результат:

- [ ] Ответ «товара нет на складе» → категория `NO_STOCK`, оба текста предлагают указать новую поставку, если дата известна.
- [ ] Короткий ответ и подробная претензия копируются отдельными кнопками, текст после копирования остаётся.
- [ ] Кнопки «Отправить в WB» нет.
- [ ] Фотоанализ показывает счётчики и суммы по вердиктам.
- [ ] Предупреждения (`warnings`) и `needsHumanReview` видны пользователю.

Приватность и UI:

- [ ] В UI нет названий моделей, провайдера, имён полей API, статусов очереди, stack trace.
- [ ] В аналитику не попадают тексты, артикулы, размеры, суммы.
- [ ] Все события из раздела 8 уходят с `source = "extension"`.
