# Контроль FBS-остатков

## Назначение

Модуль `stock_control` — bounded context для контроля FBS-остатков Wildberries и Ozon. Он хранит физический остаток организации, получает выставленные остатки и FBS-заказы через официальные API, строит рекомендации и открывает алерты. Общая карта товаров и артикулов площадок принадлежит модулю `product_matching`.

В v1 поддерживается только FBS. FBO и FBW отбрасываются адаптерами и не попадают в снимки, рекомендации и интерфейс. MarketHacker никогда не записывает остатки на маркетплейсы: продавец применяет рекомендации вручную.

## Границы модуля

`marketplace_accounts` используется только как якорь кабинета организации. Официальные API-токены продавца хранятся в отдельной vault-таблице `stock_control_api_credentials` в зашифрованном виде. Они не хранятся в `MarketplaceCredentialVault`, не зависят от Guided Connect и не используются через `wb_gateway`.

Для синхронизации достаточно неархивного кабинета и активного API-токена в vault-таблице модуля. Статус portal-подключения кабинета не определяет доступность синхронизации.

Физический остаток — одно число `physical_qty` на товар из `product_matching`. Оно изменяется только через журнал движений. Остатки маркетплейсов хранятся по кабинету, листингу и складу площадки; склады не суммируются в одну витрину.

## Ограничение тарифа и доступ

Фича тарифа: `stock_control`, `grant_scope = org`. Если фича отсутствует, backend поднимает `PlanLimitError`, HTTP API отвечает `402`.

Владелец организации управляет API-токенами, физическим остатком и настройками. Карта соответствий имеет отдельный API без ограничения фичей тарифа. Участник видит только склады и алерты привязанных к нему кабинетов.

## Синхронизация

ARQ cron запускается каждые 15 минут: `minute={0,15,30,45}`. Интервал является настройкой платформы и не передаётся продавцу.

Каждый неархивный кабинет с активным токеном синхронизируется независимо:

1. Адаптер проверяет доступ к API (ping).
2. Получает FBS-остатки по складам и изменения FBS-заказов.
3. Заказы создают идемпотентные движения физического склада.
4. Снимки обновляются отдельно по каждому складу WB или Ozon.
5. Модуль пересчитывает алерты и рекомендации.

Ошибка одного кабинета не останавливает остальные. При недоступности метода остатков допускается режим оценки по заказам; он не создаёт неизвестные остатки.

### Карта соответствий

Список артикулов для запроса остатков берётся из `product_matching`: все листинги организации на маркетплейсе кабинета (`org_id` + `marketplace`). Листинги не привязаны к отдельному кабинету; для WB-кабинета используются все WB-листинги организации.

Добавление товаров в Manager Portal: модалка «Добавить товары» (ручной ввод и файл CSV/XLSX). Файл разбирается через `POST /organizations/{org_id}/product-matching/parse` без записи в БД; строки попадают в черновик (лимит 2000). Сохранение — `POST …/commit` (all-or-nothing): upsert соответствий и опциональная установка физического остатка. Пустой остаток в строке не меняет уже заданный `physical_qty`. Endpoint `POST …/import` сохранён для совместимости, UI его не вызывает.

В Admin: пункт меню «Контроль остатков» → «Параметры» (`/stock-control/settings`) — platform TTL каталога WB Content. Org override TTL остаётся на карточке организации.

### Wildberries

Для Wildberries `mp_sku` парсится как `chrtId` (целое число). Невалидные значения пропускаются; sync продолжается.

**Hot path (каждый цикл):**

1. `GET` FBS-склады.
2. `POST stocks/{warehouseId}` только по matched `chrtId` (чанками по 1000). Если matched пуст — запросов stocks нет; заказы и алерты обрабатываются как обычно.
3. Инкрементальные FBS-заказы с `orders_cursor_at`.
4. Обновление снимков; `listed_qty = 0` выставляется только для запрошенных склад/SKU, отсутствующих в ответе.
5. `catalog_id` листинга обновляется из локальной карты `chrtId` → `nmID`.

Content API в hot path не вызывается.

**Content-каталог (редко):**

Полный обход `POST /content/v2/get/cards/list` выполняется, если:

- локальная карта отсутствует или пуста;
- `catalog_synced_at` на credential старше эффективного TTL;
- у matched-листингов пустой `catalog_id`, и в карте нет нужного `chrtId`.

При успехе карта записывается в `stock_control_wb_catalog_entries` (по кабинету, атомарная замена набора строк), на `stock_control_api_credentials` проставляется `catalog_synced_at`.

При ошибке Content: 401/403 — invalid token, старая карта не затирается; 429/5xx — sync продолжается со старой картой, stocks по matching выполняются.

**TTL Content-каталога:**

```
effective_ttl_hours = org.wb_content_catalog_ttl_hours
    if org.wb_content_catalog_ttl_hours is not null
    else platform.stock_control_wb_content_catalog_ttl_hours
```

Дефолт платформы: 24 часа. Platform default редактируется в Admin Panel (platform settings). Org override — в карточке организации в Admin Panel; `null` = platform default. Поле не входит в `PATCH /stock-control/settings` продавца.

### Ozon

`mp_sku` — числовой SKU Ozon (положительное целое в строке). Невалидные значения пропускаются; sync продолжается.

**Hot path (каждый цикл):**

1. `ping` через `POST /v1/warehouse/list`.
2. `POST /v2/product/info/stocks-by-warehouse/fbs` только по matched sku из `product_matching` (org + marketplace `ozon`), чанками. Если matched пуст — запросов stocks нет; заказы и алерты обрабатываются как обычно.
3. Инкрементальные FBS-заказы с `orders_cursor_at`.
4. Обновление снимков; `listed_qty = 0` выставляется только для запрошенных склад/SKU, отсутствующих в ответе.
5. Binding снимков и заказов по полю `sku` ответа (не по `offer_id`).

Content-каталог и картинки Ozon в v1 нет. Полный обход `product/list` / `product/info/list` на sync не выполняется.

## REST API

Префикс для Manager Portal и расширения:

`/api/v1/organizations/{org_id}/stock-control`

| Метод | Путь | Назначение |
|-------|------|------------|
| `PUT` | `/accounts/{account_id}/api-token` | Сохранить и проверить официальный API-токен |
| `DELETE` | `/accounts/{account_id}/api-token` | Удалить API-токен |
| `GET` | `/accounts/{account_id}/api-token/status` | Получить статус токена без секрета |
| `POST` | `/skus/{sku_id}/ledger/set` | Установить физический остаток через журнал |
| `POST` | `/skus/{sku_id}/ledger/adjust` | Добавить ручную дельту в журнал |
| `GET` | `/settings` | Получить настройки организации |
| `PATCH` | `/settings` | Изменить резерв и порог малого остатка |
| `GET` | `/board` | Получить страницу SKU, изображения, остатки, склады и рекомендации |
| `GET` | `/alerts` | Получить открытые алерты |
| `POST` | `/telegram/link` | Начать привязку Telegram |
| `DELETE` | `/telegram/link` | Отвязать Telegram |

Публичный webhook Telegram не входит в org-префикс:

`POST /api/v1/stock-control/telegram/webhook`

`GET /board` сначала применяет поиск `q` по внутреннему SKU и SQL-пагинацию (`page`, `pageSize`), затем строит рекомендации только для выбранной страницы. `attention=true` оставляет товары с открытым советом по превышению выставленного остатка или перераспределению, нулевым физическим остатком либо без снимков складов.

Во время синхронизации Wildberries `catalog_id` листинга обновляется из локальной карты `chrtId` → `nmID` (`stock_control_wb_catalog_entries`, периодически пополняется полным Content refresh). URL обложки в БД не хранится: доска собирает его на лету из `catalog_id`.

## Клиенты и Telegram

Manager Portal: ключи площадок — в настройках кабинета (`/accounts/{id}`), отдельно от входа в кабинет продавца. Добавление товаров (модалка) вызывает API `product_matching` (`/parse`, `/commit`, `/template`); доска и Telegram остаются на `/stock-control`. Браузерное расширение использует тот же REST API; новые экраны расширения в v1 не добавляются.

Уведомления продавца отправляет отдельный Telegram-бот. Его токен задаётся в `stock_control_telegram_bot_token` и не совпадает с токенами support- или notify-ботов. Привязка пользователя к организации хранится отдельно; сообщения фильтруются по доступным пользователю кабинетам.
